1. Analogia: a festa dos VIPs

Imagina uma festa em varios ambientes (sala, cozinha, varanda). Cada ambiente tem um tema (formal, churrasco, dance). Os convidados precisam ir pra algum ambiente.

Em vez de cada convidado decidir sozinho:

  1. Organizador escolhe o VIP de cada ambiente = a pessoa mais "tipica" do tema (quem mais bate com o ambiente)
  2. VIP "marca" o ambiente como ocupado por ele
  3. Amigos proximos do VIP (mesmo grupinho social) automaticamente vao pro mesmo ambiente, sem precisar perguntar a eles
  4. Convidados nao-amigos: vao pro proximo ambiente disputado

Mapeando pra nosso pipeline:

  • Ambientes = regioes detectadas pelo YOLO (com tipo: title, list, paragraph...)
  • Convidados = blocos vetoriais do PyMuPDF
  • VIP = anchor (bloco com maior IoS na regiao)
  • Amigos do VIP = vizinhos do anchor (mesma faixa Y vertical)

2. Algoritmo passo a passo

0Preparacao

# Inicializa todos os blocos como NAO-ATRIBUIDOS
for bloco in blocos:
    bloco._anchor_regiao = None

1Ordena regioes YOLO por confidence DECRESCENTE

regioes_sorted = sorted(regioes, key=lambda r: -r.confidence)
# mais confiantes primeiro

Por que: regioes em que YOLO esta mais seguro processadas primeiro. Anchors "consolidados" sao escolhidos primeiro, vizinhos herdam tipo de fontes confiaveis.

2Pra cada regiao em ordem, encontra o ANCHOR

for regiao in regioes_sorted:

    # Lista candidatos disponiveis
    candidatos = [b for b in blocos if b._anchor_regiao is None]
    if not candidatos:
        continue

    # Encontra o anchor (maior IoS com a regiao)
    anchor, ios_anchor = max(
        ((b, ios(b.bbox, regiao.bbox)) for b in candidatos),
        key=lambda x: x[1]
    )

    # Anchor precisa casar FORTE (IoS >= 50%)
    if ios_anchor < 0.50:
        continue   # nenhum bloco bate forte com essa regiao

    # Anchor casa
    anchor._anchor_regiao = regiao

3Propaga pra vizinhos do anchor

    anchor_y_centro = (anchor.y1 + anchor.y2) / 2
    anchor_altura = anchor.y2 - anchor.y1

    for vizinho in blocos:
        if vizinho._anchor_regiao is not None:
            continue   # ja atribuido, pula

        # Vizinho precisa estar PERTO verticalmente
        vizinho_y_centro = (vizinho.y1 + vizinho.y2) / 2
        distancia = abs(vizinho_y_centro - anchor_y_centro)
        if distancia > anchor_altura * 2:
            continue   # muito longe verticalmente

        # Vizinho precisa ter QUALQUER overlap com a regiao
        # (NAO precisa ser >= 50% como o anchor)
        if ios(vizinho.bbox, regiao.bbox) > 0:
            vizinho._anchor_regiao = regiao   # HERDA tipo

4. Anchor vs Best Match — caso onde anchor SALVA

Imagine bloco vetorial que esta na fronteira entre 2 regioes:

Bloco "- Conclusao":
  IoS com LIST: 0.45  (toca borda inferior da LIST)
  IoS com PARAGRAPH: 0.50  (toca borda superior da PARAGRAPH)
Best Match Puro
Maior IoS = PARAGRAPH (0.50)
-> bloco vira PARAGRAPH ❌

(deveria ser LIST — esta logo
abaixo de "- Hardware",
"- Software" que sao da lista)
Anchor + Propagacao
B2 "- Hardware" virou anchor da LIST.
Vizinhos do anchor: bloco "- Conclusao"
esta na faixa Y do B2.

IoS(- Conclusao, LIST) = 0.45 > 0 ✓
-> HERDA tipo LIST ✅

Propagacao do "VIP" supera
o best match local.

Esse eh o ganho real do anchor: resgate de blocos de fronteira que pelo IoS local iriam pro lugar errado mas pertencem ao mesmo grupo do anchor.

5. Trade-off — quando anchor pode propagar errado

O mesmo mecanismo que salva pode errar em casos opostos:

Bloco "- Redes" tem:
  IoS com LIST: 0.50  (era da lista correta)
  IoS com PARAGRAPH: 0.10  (raspão)

Mas o anchor da PARAGRAPH (B5 "Sistema...") esta logo abaixo,
na faixa Y de propagacao.
Anchor (caso errado)
B5 "Sistema..." virou anchor PARAGRAPH.
"- Redes" esta na faixa Y do B5.

IoS(- Redes, PARAGRAPH) = 0.10 > 0 ✓
-> HERDA tipo PARAGRAPH ❌

(deveria ser LIST porque IoS
direto era 0.50, maior!)
Best Match Puro
Maior IoS = LIST (0.50)
-> bloco vira LIST ✅

Best match local acerta nesse caso.

Por que funciona no agregado mesmo assim:

  • Casos "salvos" (bloco fronteira que propagacao acerta) sao mais frequentes que casos "errados"
  • Listas costumam ter varios items consecutivos — anchor pega bem
  • Paragrafos longos costumam ter varios blocos vetoriais — anchor une
  • Net result: +0.4pp em cobertura vs best match puro

6. Por que ordenar por YOLO confidence

# SEM ordenacao (loop natural):
R1 baixa confidence vai primeiro
Anchor cai num bloco "duvidoso"
Propaga tipo errado pra vizinhos
R2 alta confidence vem depois — vizinhos ja atribuidos, perdeu

# COM ordenacao por confidence DESC:
Regioes em que YOLO eh mais seguro processadas primeiro
Anchors "consolidados" sao escolhidos primeiro
Vizinhos herdam tipo de fontes confiaveis
Regioes duvidosas vem depois e pegam so o que sobrou
Insight: a ordem de processamento eh tao importante quanto o algoritmo. Mesma logica + ordem diferente = resultados diferentes. Por isso documentamos explicitamente.

Resumo final

O que o anchor faz:

  1. Pra cada regiao YOLO (em ordem de confidence): elege "anchor" = bloco vetorial mais sobreposto
  2. Anchor casa se IoS >= 50%
  3. Vizinhos verticais do anchor (mesma faixa Y, qualquer overlap) HERDAM o tipo automaticamente
  4. Blocos sem anchor proximo: vao pro fallback "paragraph"

Por que venceu:

  • +0.4pp cobertura: salva blocos de fronteira via propagacao
  • +0.4pp levenshtein: blocos "consistentes" no mesmo cluster
  • +0.1pp bigramas: ordem dos blocos preservada melhor
  • tempo identico: pre-processamento eh O(M*N) igual ao matching simples

Trade-off:

  • -0.3 tipos medios: vizinhos perdem diferenciacao individual
  • Pode propagar errado em casos especificos (compensado por casos onde acerta)
